# Research — 2026-08-18

## Candidates

### 1. Docker's `--memory` limits are silently unenforced on stock Raspberry Pi OS (Bookworm and Trixie alike)
- **What people hit:** On a fresh Raspberry Pi OS Lite 64-bit install, the memory cgroup controller isn't enabled by default. `docker run --memory=512m ...` is accepted with no error or warning, but the limit is never enforced — a container can consume the whole machine's RAM and OOM-kill the host instead of being capped. `docker info` does surface a warning (`WARNING: No memory limit support`) but only if you know to look at `docker info` rather than trust the flag you just passed.
- **Why it's poorly served:** This has been true since Bookworm and is still true on the 2026-04-13 Trixie release — it's not a regression, it's a standing gap. The upstream request to enable it by default was filed against `pi-gen` and closed **"not planned"**, so it will not be fixed upstream; every Pi running Docker has to know to fix it themselves. Most how-tos that mention it treat it as a one-time "add these two kernel params" step and move on — none of the ones surfaced here mention that skipping it fails *silently* rather than loudly, which is exactly the kind of gap this site exists to close.
- **Evidence:**
  - [RPi-Distro/pi-gen#917](https://github.com/RPi-Distro/pi-gen/issues/917) — request to enable memory cgroups by default in 64-bit Lite builds, closed as not planned; confirms Pi 4B, Pi 3B+, Pi 5, Pi Zero 2 W are all affected on the 2026-04-13 Trixie build.
  - [Raspberry Pi Forums: "Cgroups memory not working on RPI5 & Bookworm"](https://forums.raspberrypi.com/viewtopic.php?t=389843) and [an older thread with the same root cause](https://forums.raspberrypi.com/viewtopic.php?t=359827) — same failure recurring across OS releases.
  - [raspberrypi/linux#5933](https://github.com/raspberrypi/linux/issues/5933) — on Pi 5 specifically, the cgroup can fail to enable even *with* the correct kernel command-line parameters, which is a caveat worth checking for separately if this becomes a post about Pi 5.
  - [k3s-io/k3s#2067](https://github.com/k3s-io/k3s/issues/2067) — the same missing-cgroup problem breaking k3s on Pi, showing this isn't Docker-specific — it hits any container runtime that depends on cgroup memory accounting.
- **How to check it on the reference Pi:**
  ```bash
  # Is the kernel param present at all?
  cat /boot/firmware/cmdline.txt

  # Is the memory controller actually active in the running cgroup hierarchy (cgroup v2)?
  cat /sys/fs/cgroup/cgroup.controllers

  # Does Docker itself think it has memory-limit support?
  docker info 2>&1 | grep -i -A1 "memory"
  ```
  If `cgroup_enable=memory` / `cgroup_memory=1` are missing from the first command, or `memory` is absent from `cgroup.controllers`, or `docker info` prints a "No memory limit support" warning, the machine has the gap.
- **Possible toolkit angle:** A read-only checker that confirms whether memory cgroup accounting is actually live (not just whether the cmdline flags are present — the Pi 5 issue above shows those can disagree), and, separately, an idempotent fixer that adds the params to `cmdline.txt` with a backup, the way the existing PARTUUID script handles `cmdline.txt`. Given the site already has a `cmdline.txt`-editing script (the rpi-clone post), this would reuse that pattern rather than invent a new one.
- **Confidence:** high — multiple independent sources over several years, an explicit "won't fix upstream" from the tool that builds the OS image, and a concrete, cheap, unambiguous check.

### 2. `nmcli` ≥ 1.52 (shipped in Trixie) silently drops WiFi credentials when a provisioning script uses an abbreviated property name
- **What people hit:** Debian trixie ships NetworkManager/nmcli 1.52+, which changed how abbreviated property names resolve. Scripts that worked for years using shortcuts like `conn.autoconnect-p` now fail, because NetworkManager added a second property (`autoconnect-ports`) that also starts with `autoconnect-p`, making the abbreviation ambiguous. `nmcli` aborts with `Error: invalid property 'autoconnect-p': 'autoconnect-p' is ambiguous: autoconnect-priority, autoconnect-ports.` — but only if all properties are set in one `nmcli connection modify` call, which is the common pattern. Because the SSID/password/key-mgmt properties are set in the same call and come *after* the ambiguous one, the connection profile is left created but with no PSK and no security type: it looks configured, and never connects.
- **Why it's poorly served:** This is a breaking change in a tool, not a documented Pi-specific bug, so it doesn't show up in Pi troubleshooting guides at all — and the countless existing "headless WiFi setup with nmcli" tutorials that predate Trixie use exactly this abbreviated-property pattern, because it worked for a decade. None of them will warn you; they'll just stop working the moment someone runs them against a Trixie image. I could only find one project that has actually diagnosed and documented the root cause so far (linked below) — this is a case where the failure is likely more widespread than the visible evidence, precisely because it's new and easy to misattribute to something else (bad password, wrong SSID, router issue).
- **Evidence:**
  - [MiczFlor/RPi-Jukebox-RFID#2660](https://github.com/miczflor/rpi-jukebox-rfid/issues/2660) — the one fully diagnosed instance: exact command, exact error, exact silent-failure mechanism, and the fix (use full property names).
  - [Raspberry Pi Forums: "NetworkManager Connection Configuration File"](https://forums.raspberrypi.com/viewtopic.php?t=392436) — separate but adjacent Trixie NetworkManager confusion (connection files landing in `/run/NetworkManager/system-connections/` instead of `/etc/`), suggesting NetworkManager's on-Trixie behavior is generally under-documented right now, not just this one property issue.
  - Debian's own [`nmcli(1)` trixie manpage](https://manpages.debian.org/trixie/network-manager/nmcli.1.en.html) documents that abbreviations must be unambiguous, confirming the mechanism, but doesn't call out this specific collision or its consequences anywhere a script author would see it before hitting it.
- **How to check it on the reference Pi:**
  ```bash
  # Confirm the nmcli version in play
  nmcli --version

  # List saved connection profiles and flag any WiFi profile missing security settings
  # (a profile silently left without a psk/key-mgmt is the fingerprint of this bug)
  sudo grep -L "psk\|key-mgmt" /etc/NetworkManager/system-connections/*.nmconnection 2>/dev/null

  # Look for any local provisioning scripts that use the ambiguous abbreviation
  grep -rn "autoconnect-p[^or]" /etc /usr/local/bin /home 2>/dev/null
  ```
  Note this is a read-only audit, not proof either way on its own — a profile with no security section could also just be an intentionally open network. Treat a hit as "worth looking at the script that created it," not as confirmation.
- **Confidence:** medium — the mechanism and one real-world instance are solidly documented, but I only found that one project having actually named and fixed it, so "recurring" is closer to "recurring in principle" than "recurring in the wild" right now. Worth a second pass closer to publication to see if more reports have surfaced.
